# telescope_mount

Прошивка контроллера монтировки телескопа на ESP32.

Проект использует официальный тулчейн Espressif: **ESP-IDF + CMake**, прикладной код
на **C++** с точкой входа `app_main()`. Arduino и PlatformIO не используются.

## Статус

Этап 2 — слой движения реализован: компоненты `motion` (профиль разгона и
торможения, состояние оси, политика удержания) и `motor_hal` (ULN2003, GPTimer,
задачи осей). Логика профиля и расписания покрыта host-тестами без железа.
Сборка `idf.py build` и прогон на стенде ещё не выполнены. Джойстик, концевики,
коммуникации и логика наведения не реализованы.

## Аппаратная часть

| Компонент | Роль |
|---|---|
| ESP32-WROOM-32 DevKit | контроллер прошивки, логика 3.3 В |
| 2 × 28BYJ-48 (5 В) + 2 × ULN2003 | приводы осей «азимут» и «высота» |
| Джойстик KY-023 / HW-504 | ручное наведение (2 оси + кнопка) |
| Источник 5 В ≥ 2 А | питание приводов, общий GND с ESP32 |

Кратко по пинам: джойстик — 34 (VRx), 35 (VRy), 32 (SW); ULN2003 азимута —
25 / 26 / 27 / 14; ULN2003 высоты — 18 / 19 / 23 / 13; резерв под GPS — 16 / 17
(UART2); резерв под компас — 21 / 22 (I2C).

Подробное описание — [`docs/hardware/overview.md`](docs/hardware/overview.md)
(состав, питание, схема соединений, характеристики приводов) и
[`docs/hardware/pinmap.md`](docs/hardware/pinmap.md) (карта GPIO).

## Стек и целевая платформа

| Параметр | Значение |
|---|---|
| Фреймворк | ESP-IDF (ветка `release/v5.x`, точная версия фиксируется локально) |
| Система сборки | CMake через `idf.py` |
| Язык | C++ (точка входа `extern "C" void app_main()`) |
| Целевой чип | `esp32` — ESP32-WROOM-32 / классический ESP32 DevKit |
| ОСРВ | FreeRTOS (входит в ESP-IDF) |

## Требования

- Python 3.8+ и git
- ESP-IDF, установленный через `install.bat` / `install.sh` из репозитория Espressif
- Драйвер USB-UART (CP210x или CH340, в зависимости от платы)

## Настройка окружения

Переменные окружения ESP-IDF задаются скриптом экспорта из каталога установки.

Windows (`cmd`):

```bat
%userprofile%\esp\esp-idf\export.bat
```

Windows (PowerShell):

```powershell
. $env:USERPROFILE\esp\esp-idf\export.ps1
```

Linux / macOS:

```bash
. $HOME/esp/esp-idf/export.sh
```

Проверка:

```bat
idf.py --version
```

### Если `idf.py` не найден

Ошибка вида `"idf.py" не является внутренней или внешней командой` означает, что
окружение ESP-IDF либо не установлено, либо не активировано в текущем терминале.

1. Проверить, задан ли `IDF_PATH`, и есть ли установка:

```bat
echo %IDF_PATH%
where idf.py
where cmake
```

2. Если установки нет — установить ESP-IDF (Windows Installer или git + `install.bat`),
   см. официальную документацию Espressif.
3. Если установка есть — выполнить `export.bat` / `export.ps1` в **этом же** терминале
   и повторить `idf.py --version`.

Важно: экспорт окружения действует только на текущую сессию терминала.

## Сборка

```bat
idf.py set-target esp32
idf.py build
```

`set-target` выполняется один раз для чипа; он создаёт `sdkconfig` и очищает `build`.
Полная пересборка с нуля:

```bat
idf.py fullclean
idf.py build
```

## Прошивка и мониторинг

```bat
idf.py -p COM3 flash
idf.py -p COM3 monitor
```

Прошивка и мониторинг одной командой:

```bat
idf.py -p COM3 flash monitor
```

Выход из монитора: `Ctrl+]`.

Только мониторинг, без прошивки:

```bat
idf.py -p COM3 monitor
```

> Примечание: номер порта (`COM3`, `/dev/ttyUSB0`) зависит от платы и ОС.

telescope_mount/
├── CMakeLists.txt          корневой проект ESP-IDF

├── README.md
├── LICENSE
├── docs/
│   ├── plans/              планы разработки (0001, 0002)
│   └── hardware/           документация по железу, pinmap
├── main/                   точка входа app_main, Kconfig приложения
├── components/
│   ├── board/              единственное место с номерами GPIO
│   ├── motion/             чистая логика: профиль, дедлайны, исполнитель
│   └── motor_hal/          ULN2003, GPTimer, задачи FreeRTOS

Компоненты добавляются по мере необходимости в `components/<name>/` и не смешиваются
с `main`. Каталоги `src`, `lib`, `include` в стиле Arduino не используются.

## Тесты логики движения

Логика профиля, расписания и удержания не зависит от ESP-IDF и проверяется
обычным CMake на хосте:

```bash
cmake -S test/host -B build-host -DCMAKE_BUILD_TYPE=Debug
cmake --build build-host
ctest --test-dir build-host --output-on-failure
```

Санитайзеры включаются опцией `-DENABLE_SANITIZERS=ON`.

Проверочный прогон на стенде (двигает обе оси) включается отдельно:

```bash
idf.py menuconfig   # Application -> Run motor self-test at boot
```

По умолчанию самотест выключен. Во время движения запрещены запись NVS/flash,
OTA и тяжёлое логирование: они срывают расписание шагов.

## Правила проекта

- Номера GPIO задаются **только** в компоненте `board`; единственный источник
  истины — [`docs/hardware/pinmap.md`](docs/hardware/pinmap.md). Изменение проводки
  сначала вносится в документ, затем в код.
- Логика управления движением не зависит от джойстика, датчиков и коммуникаций:
  они передают ей уставки через чёткие интерфейсы.
- Обработчики прерываний содержат минимум кода: только флаг или отправка в очередь.
- Единица счёта — полушаг (4096 на оборот вала). Позиция меняется только после
  фактического переключения фаз, а не при подготовке шага.
- Источник шагов — GPTimer с непрерывным счётчиком и одноразовыми alarm на
  абсолютные дедлайны; `esp_timer` остаётся только отладочной альтернативой.
- Политика удержания по умолчанию — автообесточивание: обмотки под током
  греются. Удержание с таймаутом и бессрочное включаются конфигурацией оси.
