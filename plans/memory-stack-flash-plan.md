Четыре долгоживущих объекта служб и массив конфигураций осей — **автоматические переменные `app_main()`**: [main/main.cpp:405](../main/main.cpp:405), [:406](../main/main.cpp:406), [:421](../main/main.cpp:421), [:422](../main/main.cpp:422), [:430](../main/main.cpp:430). 1. **Какая именно функция исчерпала стек main.** Строка лога Wi-Fi — только последний вывод перед обнаружением.

- Пины, планировщик шагов, GPTimer, протокол фаз ULN2003, тикеты и эпохи команд.

### 4.2 Статическая RAM и линкерные регионы

| Регион | Размер | Занято статикой | Остаток региона |
|---|---|---|---|
| `dram0_0_seg` (0x3ffb0000) | 0x2C200 = 180 736 Б | `.dram0.data` 18 083 + `.dram0.bss` 20 936 + `.noinit` 1 = **39 020 Б** | **141 716 Б** |
| `iram0_0_seg` (0x40080000) | 0x20000 = 131 072 Б | vectors 1 028 + `.iram0.text` 88 799 = **89 827 Б** (68.5 %) | 41 245 Б |
| `.ext_ram.bss` | 0 | — | PSRAM нет |

Важно: 141 716 Б — это **остаток конкретного линкерного региона `dram0_0_seg`**, а не полный инициализированный heap устройства. Загрузчик и `heap_init` инициализируют несколько регионов (в том числе участки DRAM, недоступные для обычного статического размещения), и их перечень виден в логе загрузки. Поэтому:

- полный размер и свободное место heap определяются только через capabilities API (`heap_caps_get_info`, `heap_caps_get_free_size`);
- категории `INTERNAL`, `8BIT`, `DMA` пересекаются и **не суммируются**;
- свободная IRAM (41 245 Б) не является универсальной памятью под строки и сетевые буферы: обычные аллокации по умолчанию её не используют.

### 4.4 Учёт heap и статики (без двойного счёта)

Модель, которую нельзя нарушать: **стек задачи — это выделение из heap**. Поэтому перенос объектов в `.bss` и изменение размера стека влияют на доступный heap так:

| Изменение | Оценка изменения доступного heap |
|---|---|
| Перенос объектов в static, стек остаётся 8192 | **−S** (≈ −3.0…−3.6 КиБ) |
| Только уменьшение стека 8192 → 4096 | **+4096 Б** |
| Перенос в static и стек 4096 | **4096 − S** (≈ +0.4…+1.0 КиБ) |

Служебные расходы и выравнивание здесь не учтены. Промежуточный вариант «static + 8192» полезен для запаса стека, но временно **увеличивает** общее резервирование RAM: стек остаётся выделенным целиком, а `.bss` растёт на S.

Состав heap в runtime (подлежит измерению):

| Компонент | Размер | Статус |
|---|---|---|
| Остаток `dram0_0_seg` после статики | 141 716 Б | Л, но не равен полному heap |
| Стеки прикладных задач + TCB | 26 624 Б + TCB | И |
| Задачи IDF (`esp_timer` 3584, event loop 2304, tcpip 3072, задачи драйвера Wi-Fi) | от нескольких до десятков КиБ | И (конфигурация) |
| Статические RX-буферы Wi-Fi | 10 × ~1.6 КиБ | `sdkconfig:1962` |
| Динамические RX/TX-буферы Wi-Fi | по 32 дескриптора, по мере надобности | `sdkconfig:1964`, `sdkconfig:1972` |
| Буферы lwIP на сокет | оценка ≈ 11.5 КиБ на соединение, **не доказанный бюджет** | `sdkconfig:2770` |
| **Свободно / минимум / наибольший блок** | **неизвестно** | требуется измерение |

### 4.5 Предварительный резерв под веб-интерфейс (оценка, не критерий приёмки)

- Flash: код `esp_http_server` ≈ 20–30 КиБ, встроенная страница ≈ 8–20 КиБ → **30–50 КиБ** (О).
- RAM: стек задачи `httpd` 4096 (настраиваемый), буфер приёма заголовков `CONFIG_HTTPD_MAX_REQ_HDR_LEN` = 1024 (`sdkconfig:1403`), структуры соединений, плюс сетевые буферы → **≈ 25–35 КиБ** для 1–2 клиентов (О). Значения `TCP_SND_BUF` + `TCP_WND` — ориентир, а не гарантированный расход одного сокета: фактическое выделение зависит от конфигурации и нагрузки и подлежит измерению после реализации.
- Эти числа **не являются** критерием достаточности и не входят в приёмку исправления памяти. Достаточность определяется измерением после реализации сервера (раздел 7.5, группа C).
- Ограничения для того шага: страница отдаётся из `.rodata` чанками; JSON собирается в ограниченный буфер 512–1024 Б; `max_open_sockets` ≤ 2–3 с LRU-purge; короткий keep-alive; обработчики вызывают только `submitIntent()`/`arm()`/`disarm()`/`requestSafetyStop()`.

## 5. Рекомендуемый минимальный вариант и альтернативы

### 5.1 Рекомендуемый (минимальный, обратимый)

1. Зафиксировать воспроизводимую базовую конфигурацию с `CONFIG_ESP_MAIN_TASK_STACK_SIZE=8192`, **без уменьшения стека**.
2. Добавить ограниченную диагностическую опцию (heap, наибольший блок, HWM всех прикладных задач) и снять базовую линию на устройстве.
3. Перенести четыре долгоживущих объекта и массив конфигураций осей в **статическое хранение внутри функции** `app_main()`, по образцу уже существующих `access_point` и `hub`, и повторить те же измерения.
4. Только после этого решать, уменьшать ли стек main (кандидат 4096).
5. Flash 4 МиБ и разметку оформить отдельным согласованным изменением.

Что именно меняется:

| Аспект | Следствие |
|---|---|
| стек main | занятость кадра уменьшается на S; резерв стека при 8192 **не возвращается** аллокатору автоматически |
| `.bss` | растёт на S |
| доступный heap | при неизменном стеке **уменьшается** на S (см. 4.4) |
| общая RAM | перенос сам по себе её не уменьшает |
| порядок инициализации | последовательность та же; статическая инициализация происходит при первом исполнении объявления |
| время жизни и ссылки | не меняются; `control` по-прежнему получает `service` и `joystick` по ссылке, объекты живут всё время работы прошивки |
| перезапуск службы | перенос в static **не запрещает** `stop()`/`start()` существующего объекта: это операции жизненного цикла, а не разрушение и повторное конструирование. План их не добавляет и не убирает |
| деструкторы | не вызываются: `app_main` не возвращает управление (как и сейчас для `access_point`/`hub`) |
| guard-переменные | компилятор добавляет служебный объект на каждый статический объект с конструктором; **размер не заявляется без проверки ABI** |

Явно **не предлагается**: выделять службы в heap «чтобы убрать их со стека».

### 5.2 Альтернативы

- **A1 — только увеличить стек main** (8192 → 12288). Без правок исходников, но тратит heap и скрывает следующую регрессию. Допустимо как немедленный хотфикс.
- **A2 — только static, стек остаётся 8192.** Убирает конкретный вклад объектов в кадр, но **не исключает переполнения** от вложенных вызовов и увеличивает резервирование RAM на S. Промежуточный и измерительный вариант.
- **A3 — гибрид** (рекомендуемое конечное состояние): static + стек, выбранный по измерению (4096–6144).
- **A4 — реже и короче логировать heartbeat.** Сейчас малополезно: вернуться, если анализ пика это подтвердит.

### 5.3 Варианты flash (решение принято: вариант A)

**Утверждено:** вариант A — одно приложение `factory`, OTA не реализуется, слоты не резервируются, хвост 0x210000 … 0x400000 остаётся нераспределённым, файловая система и раздел ресурсов страницы не добавляются. Вариант B приведён как справка и в этой реализации не используется. Само изменение flash и разметки выполняется отдельным шагом после проверки RAM (7.1).

**Вариант A — без OTA**

| Имя | Смещение | Размер | Конец |
|---|---|---|---|
| `nvs` | 0x009000 | 0x006000 | 0x00f000 |
| `phy_init` | 0x00f000 | 0x001000 | 0x010000 |
| `factory` | 0x010000 | 0x200000 | 0x210000 |

Проверки: смещение `factory` выровнено на 0x10000, размер кратен 0x10000, конец 0x210000 ≤ 4 МиБ; пересечений нет. Нераспределённый хвост: **0x210000 … 0x400000** (1.94 МиБ). Диапазон 0x100000–0x210000 находится **внутри** раздела `factory` и свободным не является.

**Вариант B — готовность к OTA**

| Имя | Смещение | Размер | Конец |
|---|---|---|---|
| `nvs` | 0x009000 | 0x006000 | 0x00f000 |
| `phy_init` | 0x00f000 | 0x001000 | 0x010000 |
| `otadata` | 0x010000 | 0x002000 | 0x012000 |
| `ota_0` | 0x020000 | 0x1D0000 | 0x1F0000 |
| `ota_1` | 0x1F0000 | 0x1D0000 | 0x3C0000 |

Проверки: размеры слотов равны, смещения приложений выровнены на 0x10000, `otadata` выровнен на 0x1000 при размере 0x2000, сумма 0x3C0000 ≤ 4 МиБ, 256 КиБ остаётся под будущий раздел хранения. OTA **не** является требованием этой задачи.

Последствия смены разметки:

- **Способ прошивки указывается явно** (например, `idf.py flash` пишет bootloader, таблицу разделов и приложение по адресам из `flasher_args.json`). Утверждение «загрузчик не затрагивается» без проверки артефактов не делается: фактические адреса проверяются по `build/flasher_args.json` и выводу прошивальщика.
- `nvs` сохраняет смещение и размер, поэтому **ожидается** сохранение данных при отсутствии стирания и отсутствии записи в диапазон NVS. Это проверяется выбранной процедурой, а не считается доказанным по совпадению адресов.
- В текущих логах настройки AP имеют `source=kconfig`, то есть пользовательских значений в NVS нет. Для проверки сохранения нужно **заранее** выполнить тестовую запись; иначе отдельно фиксируется, что сохранность пользовательских NVS-настроек не проверялась.
- Вариант B переносит приложение с 0x10000 на 0x20000; откат — прошивка предыдущего бинарника с предыдущей таблицей.

## 7. План измерений и критерии

### 7.1 Порядок работ (утверждён владельцем)

1. Зафиксировать `CONFIG_ESP_MAIN_TASK_STACK_SIZE=8192` в отслеживаемой конфигурации; стек автоматически не уменьшается.
2. Добавить отключаемую опцию `CONFIG_APP_MEMORY_DIAGNOSTICS`: heap по capabilities, наибольший блок, HWM прикладных задач.
3. Снять базовые показатели на устройстве без питания моторов.
4. Перенести согласованные долгоживущие объекты в локальные `static` и повторить те же измерения.
5. Решение об уменьшении стека main — только по результатам измерений.
6. Flash 4 МиБ и `partitions.csv` варианта A — отдельным согласованным изменением.
7. Web-сервер в эту реализацию не входит; резерв остаётся предварительной оценкой.

### 7.2 Статические измерения

```sh
idf.py size
idf.py size-components
idf.py size-files
xtensa-esp32-elf-nm -S --size-sort build/telescope_mount.elf | tail -40
idf.py -DCMAKE_CXX_FLAGS=-fstack-usage build
find build -name '*.su' | head    # затем смотреть кадры app_main и его вызываемых
```

Размер `.bin` берётся из файла и вывода сборки. Точные `sizeof` объектов (диагностическая сборка, не коммитится): `sizeof(motor_hal::MotorService)`, `sizeof(input_hal::JoystickService)`, `sizeof(control_hal::ControlService)`, `sizeof(state_hal::StateHub)`, `sizeof(state::SystemSnapshot)`, `sizeof(wifi_config_t)`, `sizeof(StaticSemaphore_t)`.

### 7.3 Runtime-измерения (устройство, первый проход без питания моторов)

```c
esp_get_free_heap_size();  esp_get_minimum_free_heap_size();
heap_caps_get_info(&info, MALLOC_CAP_INTERNAL | MALLOC_CAP_8BIT);
heap_caps_get_largest_free_block(MALLOC_CAP_8BIT);
heap_caps_get_free_size(MALLOC_CAP_DMA);      // только DMA-capable
heap_caps_get_free_size(MALLOC_CAP_SPIRAM);   // ожидается 0
```

Стеки:

- `main`: `uxTaskGetStackHighWaterMark2(nullptr)` вызывается **из самой задачи main**, без поиска по имени;
- обе оси имеют одинаковое имя `motor_axis`, поэтому `xTaskGetHandle("motor_axis")` не даёт раздельных значений. Допустимые варианты: (а) `uxTaskGetSystemState()` со списком задач и выводом каждой записи с индексом/handle; (б) сохранённые handles через ограниченный диагностический интерфейс; (в) согласованные разные диагностические имена задач (правка исходников, требует отдельного согласия);
- HWM отражает минимальный свободный остаток стека с момента запуска задачи, а не мгновенное значение.

Правила безопасной диагностики (обязательны):

- массовое перечисление задач (`uxTaskGetSystemState`, `vTaskList`) выполняется **только при подтверждённом останове, без движения**. Espressif предупреждает, что эта функция предназначена для отладки и оставляет планировщик приостановленным на продолжительное время: в контуре с короткими дедлайнами шагов такая диагностика сама влияет на измеряемое поведение, и низкий приоритет диагностической задачи этого не устраняет;
- под нагрузкой (движение, recovery, переключение Wi-Fi) используются заранее полученные валидные handles и отдельные HWM-запросы либо согласованный сбор показателей самими задачами;
- форматирование и вывод выполняются вне моторных критических секций и не под моторными мьютексами;
- диагностический вызов не добавляется на каждый шаг;
- при lifecycle-тестах handles обновляются: handle завершившейся задачи больше не используется;
- массив `TaskStatus_t` должен иметь заведомо достаточную ёмкость; возврат 0 при слишком маленьком массиве считается **ошибкой диагностики**, а не отсутствием задач.

Оговорки по единицам и агрегатам:

- параметры стека в `xTaskCreate` в ESP-IDF — байты; единицу возврата HWM и столбца стека в `vTaskList()` подтвердить по заголовкам v6.1;
- разрешение тика 10 мс (`CONFIG_FREERTOS_HZ=100`), поэтому короткие пики ловятся только HWM;
- сумма минимумов отдельных регионов может относиться к разным моментам времени и не является синхронным снимком: использовать как консервативный показатель;
- ранние измерения heap допустимы как промежуточные точки, но **не заменяют** baseline после запуска всех служб;
- стартовые области `heap_init` нельзя выдавать за текущий свободный heap;
- расходы самой диагностики входят в бюджет и учитываются при сверке результатов.

### 7.4 Матрица сценариев

| № | Сценарий | Что фиксировать |
|---|---|---|
| 1 | Загрузка до heartbeat, моторы без питания | HWM main и всех прикладных задач, free/min/largest heap, регионы heap |
| 2 | Нейтраль 5 минут | дрейф heap, HWM control и joystick |
| 3 | Движение — отдельный контролируемый этап с питанием моторов | HWM обеих осей и control только по заранее полученным handles; минимум свободного heap, наибольший блок; массовое перечисление задач запрещено |
| 4 | Останов (плавный и немедленный) | heap до/после, HWM |
| 5 | Восстановление через `acknowledgeFault()` | HWM, heap, отсутствие регрессии защёлки |
| 6 | Переключение Wi-Fi двойным нажатием выкл/вкл, ×10 | дрейф heap, HWM `wifi_ap`, задержка RF-рекалибровки |
| 7 | 20 × `stop()`/`start()` для control, joystick и Wi-Fi | остаток heap и наибольший блок в сопоставимых состояниях, число задач, ресурсы |
| 8 | Неуспешные пути старта (невалидный mapping, таймаут радио) | возврат heap к исходному уровню |

Порядок lifecycle-операций обязателен: сначала останавливается `ControlService` как единственный исполнитель моторных операций, затем используемые им службы (`JoystickService`, `MotorService`); запуск выполняется с соблюдением зависимостей в обратном порядке. Handles после перезапуска обновляются, handle завершившейся задачи не используется.

### 7.5 Критерии

**A. Приёмка исправления памяти (обязательно)**

1. Отсутствие `vApplicationStackOverflowHook` во всех сценариях 1–8.
2. Main: при 8192 — свободно ≥ 2 КиБ; при 4096 — ≥ 1 КиБ (только после подтверждения измерением).
3. Каждая остальная прикладная задача: свободно ≥ 1 КиБ после сценариев 3–6.
4. Межсборочная сверка бюджета: изменение свободного heap между базовой и исправленной сборками сопоставляется с изменением статической RAM (`.bss`/`.data`), размеров стеков и диагностических выделений. Ожидаемое снижение из-за переноса объектов в static не считается регрессией; фиксированный допуск в КиБ между разными компоновками не задаётся. То же относится к наибольшему свободному блоку: общий свободный объём и максимальный непрерывный блок — разные показатели, обязательная разница между компоновками не требуется.
5. Внутрисборочная проверка: двадцать циклов жизненного цикла и десять переключений Wi-Fi в сопоставимых состояниях не дают необъяснимого накопления выделений; проверяются остаток heap, наибольший блок, число задач и ресурсы. Рост числа свободных блоков сам по себе не считается доказательством утечки.

**B. Предварительные ориентиры для web (информационно, не приёмка)**

- свободный heap в худшем сценарии ≥ 35 КиБ и наибольший блок ≥ 12 КиБ — цель, подлежащая проверке после реализации;
- если ориентир не достигается, это открывает отдельную задачу о количестве буферов Wi-Fi/lwIP.

**C. Измеренная достаточность после реализации сервера**

- отдельный проход по сценариям 1–8 с включённым HTTP-сервером и 1–2 клиентами;
- проверка стека задачи `httpd`, числа соединений и отсутствия накопительного роста занятой памяти при повторных запросах.

**Инженерные политики (не критерии корректности)**

- занимать не более 50 % раздела приложения — политика запаса, а не обязательное условие;
- исчезновение предупреждения `Detected size(4096k) larger…` — ожидаемый побочный эффект согласования flash, отдельная проверка в рамках изменения разметки.

## 8. Риски, откат и решения для владельца

### 8.1 Риски

- Перенос в static превращает вклад объектов из стекового в статический, но **увеличивает** резервирование RAM при неизменном стеке (4.4). Экономия появляется только вместе с уменьшением стека, и только по измерению.
- Изменение `sdkconfig.defaults` действует на **вновь сгенерированный** `sdkconfig`; локальный файл нужно перегенерировать или править согласованно.
- Уменьшение стека main до измерения вернёт ровно тот дефект, который исправляется.
- Оценка веб-слоя может не поместиться; это отдельная задача, а не изменение этого плана.
- Уровень оптимизации Debug увеличивает и flash, и стеки; его изменение сдвинет все базовые линии, поэтому здесь он не трогается.
- Устранение стартового дефекта **не блокируется** выяснением стандарта C++ и получением всех возможных отчётов; измерения обязательны только перед уменьшением стеков и заявлениями об экономии RAM.

### 8.2 Откат

- Код: `git restore main/main.cpp` — других отслеживаемых исходников план не касается.
- Конфигурация: вернуть `sdkconfig.defaults`; локальный `sdkconfig` не отслеживается и может быть перегенерирован.
- Разделы: прошить предыдущую таблицу и предыдущий образ выбранной процедурой. `erase-flash` по умолчанию не применяется.
- Если static-объект поведёт себя неожиданно, запасной путь — A1 (стек 12288 без правок исходников).

### 8.3 Принятые решения владельца (2026-11-15)

1. **OTA не реализуем**, место под слоты не резервируем. Выбран вариант A: `factory` 0x010000 / 0x200000, хвост 0x210000 … 0x400000 нераспределён. Файловая система и раздел ресурсов страницы сейчас не добавляются.
2. `CONFIG_ESP_MAIN_TASK_STACK_SIZE=8192` фиксируется в отслеживаемой конфигурации. **Стек main автоматически не уменьшается**; уменьшение — отдельное решение после измерений.
3. Диагностика оформляется отключаемой опцией `CONFIG_APP_MEMORY_DIAGNOSTICS`; правила 7.3 обязательны; её собственные расходы учитываются в бюджете.
4. Сначала исправление и диагностика RAM, затем отдельным изменением — согласование flash с 4 МиБ и `partitions.csv`; `erase-flash` по умолчанию не применяется.
5. Web-сервер в эту реализацию не входит; резерв под web — предварительная оценка, а не обещание достаточности.
6. Моторный протокол, GPTimer, пины, защёлки, арбитраж и порядок блокировок не меняются.
7. Коммиты и push — только по отдельному разрешению.

### 8.4 Что остаётся открытым

- способ различения двух задач `motor_axis` при измерении HWM: заранее полученные handles против отдельных диагностических имён;
- уменьшение стека main до 4096 — после измерений;
- конкретная процедура прошивки при смене разметки и проверка адресов;
- является ли ориентир web-резерва требованием уже сейчас.

## 11. Формат отчёта по результатам

Отчёт содержит отдельно:

- изменения кода и конфигурации (файл, строка, назначение);
- результаты сборки (успех или ошибки, предупреждения);
- размеры flash и статической RAM (`idf.py size`, карта линковки);
- измерения heap и стеков до/после с точками измерения и сценариями;
- невыполненные проверки и причины.

Экономия RAM или достаточность стеков **не заявляются без измерений**. Если устройство недоступно, выдаются точные инструкции измерений, а аппаратная приёмка остаётся незавершённой.
